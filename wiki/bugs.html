14. Known bugs & rough edges

A dedicated page from the 2004scape Progressive build 254 coverage audit.

Expanded from the original pass with exact file locations, line-level detail, and a few additional findings surfaced while chasing down the originals. Nothing in this section reflects a code change — it's the audit trail for future fix work.

Content bugs

WhereIssue
Priest in PerilQuest is complete and its reward is wired, but the 3 prayers it should unlock (Retribution, Redemption, Smite) don't exist anywhere in the repo. Worse than a missing-content gap: prayers.dbrow/prayers.constant/prayer.rs2 have no quest-unlock mechanism at all today — every prayer's gate in ~prayer_checks is a pure level check (stat_base(prayer) < ...). Adding these 3 prayers means building the unlock plumbing from scratch, not just adding 3 data rows. Prayer effects themselves are hard-coded per-prayer in skill_combat/scripts/player/player_combat_stat.rs2 (e.g. check_protect_prayer), which would also need new branches for Smite's prayer-drain-on-hit and Retribution's on-death AoE.
Demon SlayerThe todo: this should be instanced per player comment undersells the gap. Concretely: the silverlight key is dropped as a world-visible ground item at a fixed shared coordinate (obj_add(0_50_154_25_41, silverlight_key_3, ...)) — any nearby player can see/loot it. Delrith himself is a single shared world NPC, located via npc_find and mutated in place (npc_changetype, npc_statheal) rather than spawned per player. Most importantly: there is no instancing infrastructure anywhere in the engine — an exhaustive search of the zone system (Zone.ts, ZoneGrid.ts, ZoneMap.ts) and the entity model turned up zero per-player zone/area concept. Fixing this properly means building a new engine feature, not patching a quest script.
Ernest the ChickenThe broken path is the secret-bookcase door, not the lever. In quest_haunted.rs2, manor_bookcase_door scans for bookcase locs via loc_findallzone and the author's own comment says it plainly: "This is borked for opening the doors now... Gotta think through how to make this work with find all zone." The lever path (hauntedleverup) works because it takes a different, non-loc_findallzone code path to the same destination.
Family CrestReward call in quest_crest.rs2 passes ^squire_questpoints instead of its own constant. The correct constant, ^crest_questpoints, already exists in general/configs/quest.constant (line 71) and is simply never referenced — both constants currently equal 1, so the bug is silently harmless today, but would misreport if either value ever changes. A one-line fix once someone points at it.
Plague CityGenuinely ambiguous, not just unaudited. quest_elena/scripts/doors.rs2 hard-locks one of two adjacent plague-house doors (loc_2534) while the other (loc_2535) works. The developer's own comment cites two archived quest-guide sources (RuneHQ, Zybez, both via web.archive.org) trying to determine which physical door should be functional, and ends with "todo probs not right but yolo in 225 seems only 1 door is the correct one." Resolving this needs an external, period-accurate source beyond what's in the repo.
Debug quest-name listcontent/scripts/general/configs/quest.enum (a dev cheat-menu tool, not the player quest journal) stops at index 53 ("Priest In Peril") and is missing exactly 3 entries: Nature Spirit (quest_druidspirit), Death Plateau (quest_death), Troll Stronghold (quest_troll) — all three fully implemented quests, just absent from this one debug list.
Background NPC dead endsConfirmed real, and the mechanism is now concrete: e.g. area_ardougne_west/configs/man.npc defines w_ardougnecitizen1 through 6 with op1=Talk-to, but man.rs2 only implements handlers for 2 of them, with a comment reading "TODO: Try to find out if Jagex ever coded any dialogue for these npc" next to the unhandled ones. No master list of all ~27 exists in the repo; this would need a full per-area sweep of op1=Talk-to entries against their matching opnpc1 handlers to enumerate exhaustively.

Engine bugs & stubs

WhereIssue
Script VM local arraysDEFINE_ARRAY / PUSH_ARRAY_INT / POP_ARRAY_INT (engine/src/engine/script/handlers/CoreOps.ts) throw "unimplemented" unconditionally, ignoring their operands entirely. This isn't a stub with unused scaffolding sitting nearby — ScriptState has no array-local storage at all today (only flat intLocals/stringLocals). A real fix means adding a new parallel local-array structure to the VM, matching the official opcode encoding, not filling in an existing gap.
P_OPHELDThe protected "operate held item" trigger (engine/src/engine/script/handlers/PlayerOps.ts) throws "unimplemented". The comparable working trigger, P_OPLOC, resolves against state.activeLoc; no equivalent held-item-context field exists on script state today, so this needs new state threading, not just a function body.
Friends server world-shutdown gapMore precise than previously described: individual players do get correctly logged out of the friend server during shutdown (removePlayer() posts player_logout per player). What's actually missing is a world-level disconnect notice — there's no WORLD_DISCONNECT-equivalent opcode anywhere in FriendsClientOpcodes/FriendsServerOpcodes, and FriendServer.ts's socket close handler is a literal no-op: socket.on('close', () => {}).
Inventory.shift()Confirmed fully dead: a repo-wide search for .shift( found zero call sites against an Inventory instance anywhere in engine/src or content/scripts. Its own sort comparator is also broken — it compares Item objects directly (+(a > b) || -(a < b)) rather than a field, which isn't a meaningful ordering. A stronger finding than "flagged for review": this code doesn't work even if called.
Duplicate bot task base classNew finding: a full second copy of the bot task base class and BuryBonesTask exists at engine/src/engine/bot/BotTask.ts (792 lines), superseded by tasks/BotTaskBase.ts + tasks/UtilTasks.ts (which is what BotGoalPlanner.ts actually imports) but never removed — dead legacy duplication.

Progressive bot AI — scope, not bugs

Two items from the original audit are re-confirmed here as accepted scope limitations, not defects to fix: bots have zero quest-awareness — a full search of BotGoalPlanner.ts and every file under tasks/ found no quest state tracking, quest triggers, or quest-driven task of any kind, not even scaffolding. And bone-burying isn't real prayer training — BuryBonesTask is pure inventory arithmetic (remove bones, grant XP on a cooldown) with a comment admitting it "simulate[s] the outcome" of the real interaction, rather than walking to an altar and using it. Progressive's bot AI is a gathering/combat/economy simulator; teaching it to solve a 56-quest chain would be a separate project on the scale of everything else in this wiki combined.
